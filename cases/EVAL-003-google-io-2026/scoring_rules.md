# EVAL-003 结果评分细则(ScoringRules.md)

> 配合 `IO2026_GroundTruth.md` 使用。Ground Truth 只放事实,本文档定义"如何按事实判分"。
> 8 家 Agent 分别评分时,**评分者按本文档独立生成判定**,不引用其他家的判定结果(避免锚定)。
> v0.1 · 2026-05-19 keynote 当天

---

## 一、四档评分标准

| 符号 | 含义 | 得分 |
|-----|------|------|
| ✅ | **命中** —— 与实际发布完全一致或高度吻合 | +1.0 |
| 🔶 | **部分命中** —— 方向对但细节有偏差 | +0.5 |
| ❌ | **未命中** —— 与实际发布不符,或预测的产品根本没发 | 0 |
| 🚫 | **错误预测** —— 自信地预测了完全不存在的产品/功能 | -0.5 |
| ⬜ | **未预测** —— Agent 未涉及 | 不计入分母 |

**结果分计算:** 
```
结果得分 = (各预测项得分之和 / 有效预测项总数) × 100
```

**综合分计算:**
```
综合得分 = 过程分 × 40% + 结果分 × 60%
```

## 二、关键判定细则(避免锚点不一致)

### 2.1 版本号偏差判定

| 预测内容 | 实际发布 | 判定 |
|---------|---------|------|
| Gemini 3.5 Flash / Pro / Ultra | Gemini 3.5 Flash 今日发布 | ✅ 命中(版本号 + 系列对) |
| Gemini 3.2 Flash | Gemini 3.5 Flash | 🔶 部分对(Flash 系列对,版本号偏差) |
| Gemini 4.0 | 未发布 4.0 | ❌ 未命中 |
| **押"Gemini 3.5 Pro 当天发布"** | **6 月发布(预告)** | **🔶 部分对**(版本号对,发布状态错) |
| Wear OS 6 | Wear OS 7 | ❌ 未命中(版本号错) |
| Wear OS 7 | Wear OS 7 | ✅ 命中 |

### 2.2 "已发布事件"判定(关键规则!)

Agent 把**已经发生的事件**包装成"I/O 预测"——这是评测最容易争议的点。规则:

| 已发生时间 | Agent 预测语气 | 判定 |
|----------|--------------|------|
| **5/12 Android Show 已发布**(如 Pause Point / Quick Share / Googlebook / Gemini Intelligence / Noto 3D Emoji 等) | Agent 说"I/O 会发 X"或"I/O 极高置信度押 X" | **🔶 部分对**(方向对,但 keynote 主台未重复,属"已开奖" not "未来预测") |
| **4/15 macOS Gemini app 已发布** | Agent 说"5/12 上线"或"I/O 发布" | 🔶 部分对(产品存在但日期错位) |
| **2/18-3/5 Pixel 10a 已发布** | Agent 说"I/O 发布 Pixel 10a" | ❌ 未命中(已发生事件) |
| **2/19 Gemini 3.1 Pro 已发布** | Agent 说"I/O 会发 3.1 Pro 稳定版" | ❌ 未命中(已发生事件) |
| **11/18/2025 Antigravity 已发布** | Agent 说"I/O 会发 Antigravity 升级" | ✅ 命中(I/O 确实发了 Antigravity 2.0) |
| **11/18/2025 Antigravity 已发布** | Agent 说"I/O 会发布 Antigravity 这个全新 IDE" | 🔶 部分对(产品已存在,但 2.0 升级是真,框架错位) |

**核心原则:** **5/12 Android Show 已发布的内容**应算 🔶 而非 ✅。即便 Agent 在 5/12 之前(5/8-9)就预测了对的方向,从评分公平角度,这些 keynote 主台未重复的内容**只能算"方向对"**。

### 2.3 边界条件细则

#### Android Halo
- ✅ 命中:Agent 明确提及"agent 实时更新 UI 空间"或"Halo"
- 🔶 部分对:Agent 含糊提"Gemini 在 Android 系统层的 agent 集成"
- ❌ 未中:Agent 只说"Android 17 重大更新"无具体 UI 空间描述

#### Universal Cart
- ✅ 命中:Agent 明确提"跨应用统一购物车 / 跨 Search/Gemini/YouTube/Gmail / 自动追踪价格 / 不兼容检测"
- 🔶 部分对:Agent 含糊提"Google 升级了购物搜索"或"Agentic Shopping 能力"
- ❌ 未中:Agent 只说"Google Pay / Google Wallet 更新"

#### Gemini Spark
- ✅ 命中:Agent 明确押"Gemini Spark"作为 always-on 24/7 个人 AI agent
- 🔶 部分对:Agent 押"Project Mariner 继任者 / Gemini Agent / 24/7 AI 助手"但没用"Spark"具体命名
- ❌ 未中:Agent 没有任何"个人 AI agent"维度预测

#### Antigravity 2.0
- ✅ 命中:Agent 预测"Antigravity GA / 订阅层 / 桌面 app / 全球开放"
- 🔶 部分对:Agent 仅提"Antigravity 作为 IDE 升级"或框架错位称之为"全新发布"
- ❌ 未中:Agent 完全未提 Antigravity

#### Android XR 智能眼镜
- ✅ 命中:明确押"I/O 会有 XR 眼镜实机演示"+ 至少提一家合作伙伴(Samsung/Warby Parker/Gentle Monster/XREAL)
- 🔶 部分对:仅含糊押"XR 眼镜会有进展"无具体合作伙伴
- 🔶 部分对:押"Samsung Galaxy Glasses 上市"——keynote 上是 preview 不是上市,押"亮相"对,押"上市"错位

### 2.4 模糊预测判定

- "Gemini 会更强"、"Android 更智能" → ❌ 不算预测,不计入分母
- "可能会有 AI 改进" → ❌ 不算预测,不计入分母
- "Gemini 3.5 Pro 1M token 上下文" → 算预测项(有具体参数)

**case 文档原则:只摘"可验证的具体陈述"。**

## 三、追问内容的评分规则(关键 / 最终版)

追问 1-3 三种内容性质不同,处理方式也不同:

| 追问 | 内容性质 | 处理方式 |
|------|---------|---------|
| 追问 1 自我修正 | **元行为**(改 Section 5)| **清洗 Section 5,不直接给分** |
| 追问 2 押注 | **元选择**(从 Section 5 挑最有把握的)| **不入结果分**,只标记命中状态做文章彩蛋 |
| 追问 3 "最大意外" | **全新预测**(Section 5 没有的)| **进结果分,作为 1 条独立新预测项** |

### 3.1 追问 1 的"自我修正"——数据清洗

Agent 在追问 1 可能会修正主报告里的预测,典型处理:

| Agent 修正行为 | 评分处理 |
|--------------|---------|
| "我把 Pixel Watch 5 错放到 I/O,应在秋季"→ 主动撤回 | **从 Section 5 分母移除该条** |
| "我把 X 置信度从高调到低" | **按修正后版本评**(下调后的置信度可能让该条变成"未做明确预测") |
| 维持原预测 + 给出 I/O vs MbG 分工框架 | 按主报告原版本评 |
| 修正方向但语气模糊("可能会推迟") | 按主报告原版本评 |

**核心原则:鼓励 Agent 诚实修正,所以撤回不算扣分,修改按新版本评。这影响的是分母(有效预测项数),不是分子(命中数)。**

### 3.2 追问 2 的"赌上职业声誉押注"——只做彩蛋,不入分

**原因:** 追问 2 押注本质是"从 Section 5 里挑一条最有把握的",这条预测在 Section 5 已经评过了,不应该重复算分。

**评分时处理:**
- 标记押注的具体内容(从追问原文提取)
- 标记命中状态:✅ / 🔶 / ❌(简单标注,不算分)
- 作为文章"彩蛋表"素材输出

**例如:**
- Claude 押 Gemini 3.2 Flash → 实际是 3.5 Flash → 标 🔶,**不入分**
- Genspark 押 Agentic Coding → Antigravity 2.0 全球开放 → 标 ✅,**不入分**

### 3.3 追问 3 的"最大意外"——进结果分,作为 1 条独立新预测项

**原因:** 追问 3 押的"意外"是 Section 5 没有的全新预测,有客观开奖结果,应当和主报告其他预测一视同仁。

**评分处理:**
- 作为 1 条独立预测项,加入 Section 5 的分母
- 按 ✅/🔶/❌/🚫 判定,与 Section 5 同样的权重

| 情况 | 判定 |
|------|------|
| 押的产品/方向真的发了 + 在 keynote 之前确实未广泛流传 | ✅ 命中(真意外,+1.0) |
| 押的产品/方向真的发了,但已广泛预期(如 Antigravity) | 🔶 部分对(押对但不算"意外",+0.5) |
| 押的产品/方向完全没发 | ❌ 未中(0) |
| 押的产品/方向被 Agent 包装成"全新",但实际已存在 6+ 月 | 🔶 部分对(框架错位但底层预测立得住,+0.5) |
| 押的产品/方向是已发生事件(如 Pixel 10a 已发,押"会发 10a 作为意外") | 🚫 错误预测(-0.5,因为是已发生事件) |

### 3.4 评分时必须看追问原文

| 内容 | 必须看追问原文? |
|------|--------------|
| 追问 1 是否修正主报告预测(影响 Section 5 分母) | ✅ 必须 |
| 追问 2 押注的具体内容(只标记命中,做彩蛋) | ✅ 必须 |
| 追问 3 押的"意外"的完整命名和理由(进分母评分) | ✅ 必须 |

**只看 EVAL Section 6 快评不够**,因为快评是评测者提炼,不能替代原始证据。

### 3.5 最终结果分公式

```
分子 = Section 5 主报告各预测项得分之和 + 追问 3 押注得分
分母 = Section 5 有效预测项数(已应用追问 1 清洗) + 1(追问 3 这条)

结果得分 = (分子 / 分母) × 100
```

**追问 2 押注不进公式,只单独标记命中状态。**

## 四、评分时的常见误判防范

### 误判 1:把"已发生事件"判 ✅
- **错误示例:** Agent 押"I/O 发 Gemini 3.1 Pro" → 判 ✅(因为 Gemini 3.1 Pro 是真实存在的)
- **正确:** 应判 ❌,因为 3.1 Pro 在 2/19 已发,**这不是 I/O 预测**

### 误判 2:Wear OS 6 因细节匹配判 ✅
- **错误示例:** Agent 押"Wear OS 6 + Material 3 + 10% 续航" → 判 ✅(因为细节匹配 2025/5 的 Wear OS 6)
- **正确:** 应判 ❌,实际是 Wear OS 7,版本号错

### 误判 3:5/12 内容判 ✅
- **错误示例:** Agent 在 5/8 押"I/O 会发 Googlebook" → 判 ✅(因为 Googlebook 确实存在)
- **正确:** 应判 🔶,因为 5/12 已发,keynote 主台未重复

### 误判 4:Antigravity 框架错位
- **错误示例:** Gemini 把"Antigravity"包装成"大多数人没预料到的最大意外" → 判 ✅(因为 I/O 真的发了 Antigravity 2.0)
- **正确:** 应判 🔶,因为产品已存在 6 个月,Antigravity 2.0 升级是真的,但"全新"和"意外"框架错

## 五、评分流程(每家执行)

### 5.1 准备阶段(每家评前)

读完以下文件(按优先级):
1. **GroundTruth.md** —— 熟悉实际发布(15 分钟)
2. **本 ScoringRules.md** —— 熟悉判定细则(10 分钟)
3. **case 文档** —— 熟悉 Prompt + 应知清单(5 分钟)
4. **EVAL_xxx_complete.md** —— 该家的结构化测试记录(包含 Section 5 预测项 + Section 6 追问快评)
5. **该家追问 1-3 回答原文**(从飞书/PDF 拿,**必须**)
6. (可选)主报告原文 —— 押注表述模糊时回查

### 5.2 评分步骤(最终版)

1. **主报告 Section 5 预测项逐条评:**
   - 提取该家所有可验证预测项(约 25-30 条)
   - 逐条对照 GroundTruth.md,标 ✅/🔶/❌/🚫
   - 核对"已发生事件"陷阱(本文档 2.2 节)
   - 核对版本号偏差(本文档 2.1 节)
   - 统计有效预测项(模糊陈述不计分母)

2. **追问 1 清洗 Section 5:**
   - 看追问 1 原文,识别 Agent 是否修正/撤回了 Section 5 的预测
   - 撤回的预测 → **从分母移除**
   - 修改的预测 → **按新版本评**

3. **追问 2 押注 → 只做彩蛋,不入分:**
   - 看追问 2 原文,识别押注的具体内容
   - 标记命中状态:✅/🔶/❌(简单标注)
   - **不入结果分公式**,作为"文章彩蛋表"素材输出

4. **追问 3 "最大意外" → 进结果分作为 1 条新预测:**
   - 看追问 3 原文,识别押的"意外"
   - 按 ✅/🔶/❌/🚫 判定(本文档 3.3 节)
   - **加入 Section 5 的分子分母**,与主报告其他预测一视同仁

5. **算结果分(最终公式):**
   ```
   分子 = Section 5 主报告各预测项得分 + 追问 3 押注得分
   分母 = Section 5 有效预测项数(已清洗) + 1(追问 3 这条)
   
   结果得分 = (分子 / 分母) × 100
   ```
   
   注意:追问 2 押注不进公式。

6. **算综合分:**
   ```
   综合分 = 过程分 × 40% + 结果分 × 60%
   ```

7. **总结输出(每家):**
   - 命中率表(Section 5 + 追问 3 各几条 ✅/🔶/❌/🚫)
   - 追问 1 修正情况(撤回/修改了几条)
   - 追问 2 押注命中状态(单独标记,做彩蛋)
   - 追问 3 押注命中状态(已计入结果分)
   - ⚠️ 模糊项列表
   - 结果分(满分 100)
   - 综合分(过程 40% + 结果 60%)
   - 一句话定性

## 六、给评分者的最终提醒

- **不要看其他家的评分结果再评本家** —— 避免锚定
- **每家独立按 GroundTruth + 本文档评分**
- **遇到边界模糊时,优先按本文档 2.3 节判**
- **遇到本文档未覆盖的情况,标 ⚠️ 等用户/同事人工裁定**
- **追问回答原文必须看,不能只看 EVAL Section 6 快评**

## 七、推荐工作流(分批评)

8 家分 2 个新对话评比一家一对话效率高:

| 新对话 | 评什么 | 文件清单 |
|------|------|---------|
| **新对话 1** | 用户测的 4 家(ChatGPT / Genspark / Claude / Gemini)| GT + Rules + case + 4 份 EVAL(预处理后含追问全文)|
| **新对话 2** | 同事测的 4 家(Manus / Kimi / GLM / MiniMax)| GT + Rules + case + 4 份 EVAL(预处理后含追问全文)|

**为什么这样分:**
- 同一新对话内 4 家锚点一致(连续评不漂移)
- 把 COI 关键的 Claude 跟 ChatGPT 放一起,可以"先评 ChatGPT 校准手感再评 Claude"
- 4 家 × ~3000 tokens = ~12000 tokens 文件,context 撑得住

### 预处理 EVAL 文档(评分前必做)

把每家 EVAL_xxx_complete.md 的 Section 6 追问回答从**外挂链接**复制粘贴成**原文嵌入**,变成"自包含 EVAL 文档"。

预处理后效果:
- ✅ 每家只需要 1 个 EVAL 文件就包含追问全文
- ✅ 新对话只需要带 7 个文件(GT + Rules + case + 4 份 EVAL)
- ✅ 不需要再单独贴追问原文
